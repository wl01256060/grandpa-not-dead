# 遊戲機制檢核評分

用六個業界常用的設計框架，檢核使用者提供的遊戲機制與內容，判斷遊戲是否夠有趣、複雜度是否適中，並提出可執行的改善建議。

## 使用時機

- 使用者提供規格書、設定集、規則說明或對話整理，想知道遊戲是否夠好玩、太單薄或太複雜
- 使用者修改機制後，想比較前後版本
- 使用者只想檢核其中一兩個框架時，只跑那幾項，其餘略過

## 步驟

### 1. 蒐集與整理素材

1. 讀完使用者提供的所有文件與內容。
2. 先整理出「目前的遊戲」摘要，包含：
   - 目標體驗（使用者想讓玩家感受到什麼）
   - 一局流程與時長
   - 玩家人數與角色
   - 玩家可以做的所有動作
   - 勝負條件
   - 資源與數值（分數、HP、道具等）
3. 文件互相矛盾時，列出矛盾點並註明採用哪一版；無法判斷時先問使用者。
4. 缺少評分所需的關鍵資訊（例如沒寫勝負條件）時，該項標記「資訊不足」，不要自行假設成事實。若必須假設才能繼續，明確寫出假設內容。

### 2. 逐一檢核六個框架

每個框架給 1 到 5 分，並附上依據與證據（引用使用者文件裡的具體規則或內容）。

評分基準：
- 5：完整且有深度，幾乎沒有問題
- 4：大致完整，有小缺口
- 3：基本可用，但有明顯單薄或過度複雜之處
- 2：有關鍵缺口，會直接影響體驗
- 1：缺乏或嚴重失衡

#### A. MDA（機制 → 動態 → 美學）

檢查問題：
- 目標美學是否明確？（例如被背刺又想笑、緊張、爆笑）
- 每個機制能否對應到至少一種目標美學？列出對應不到的機制（可能是多餘的複雜度）
- 每種目標美學是否有機制支撐？列出缺乏支撐的美學（太單薄的地方）
- 機制實際會產生什麼動態？是否和目標美學一致？

#### B. 核心循環

把循環分成三層並畫出文字版流程（例如 搜索 → 取得道具 → 送禮 → 反應 → 結算）：
- 秒級循環（每幾秒重複的動作）
- 回合／每日循環
- 整局與重玩循環

檢查問題：
- 每一圈是否至少有一個「有意義的選擇」？有意義的選擇須有取捨、沒有明顯最佳解、後果看得到
- 每一圈是否有清楚的回饋與獎勵？
- 循環會不會隨時間變化或升級？第一回合和最後一回合的體驗是否不同？
- 同時需要顧的事是否過多？

#### C. 形式元素（Fullerton）

逐項檢查八個元素是否明確、是否互相支撐：
玩家、目標、流程、規則、資源、衝突、邊界、結果。

檢查問題：
- 衝突從哪裡來？衝突是否夠強？（衝突弱通常代表無聊）
- 核心規則能否在一分鐘內講完？
- 有沒有規則只是為了修補另一條規則而存在？

#### D. 動詞清單與互動矩陣

1. 列出玩家可做的所有動詞。
2. 建立互動矩陣，至少包含：玩家對玩家、玩家對主要 NPC、玩家對場景／世界、玩家對系統（數值、事件）。每格填入對應的動詞，空格要標出來。

檢查問題：
- 核心動詞數量是否適中？派對遊戲通常 3 到 6 個核心動詞
- 每個動詞是否能用在多種情境？（深度比數量重要）
- 是否有動詞永遠是最佳選擇，讓其他選擇形同虛設？
- 玩家對玩家的互動是否足夠？

#### E. 情緒曲線

把一局遊戲依時間切段，標出每段預期的玩家情緒（期待、緊張、爆笑、背叛、放鬆等），用文字或簡單的文字圖表呈現。

檢查問題：
- 有沒有長時間的平線（無聊時段）？
- 高峰是否太密集造成疲乏？
- 是否有逐漸升高的節奏和一個明確的高潮？
- 結尾是否有收束感，讓人想再玩一局？

#### F. 經濟與平衡（Machinations 思維）

列出主要資源（分數、HP、道具、行動次數等）的來源、流向與消耗。

檢查問題：
- 是否存在必勝法或明顯的最佳策略？
- 領先者是否會越滾越大（滾雪球）？
- 落後者是否有翻盤機會？
- 角色或能力之間是否明顯不平衡？

### 3. 綜合判斷趣味性與複雜度

- 給出整體判斷：太單薄、適中、或太複雜，並說明主要原因
- 指出「深度」與「複雜度」的關係：好的設計用少量規則創造大量變化
- 參考基準（派對遊戲）：
  - 規則解釋時間 3 分鐘內
  - 核心動詞 3 到 6 個
  - 玩家同時需要追蹤的資訊不超過 3 到 4 項
  - 每一回合至少有一個有意義的選擇

### 4. 彙整問題點

在提出建議之前，先把六個框架找到的問題彙整成一張表，讓讀者先看清楚「哪裡有問題」，再看「怎麼改」：

- 每個問題給一個編號，用一句話寫出具體現象（引用規則或內容），不要只寫框架名稱
- 標出影響的框架（可以多個）
- 標出嚴重度：高（直接導致分數低於 3）、中（扣分但不致命）、低（規則不清或小缺口）
- 依嚴重度排序；同一個根本原因造成的問題合併成一條
- 表格欄位：編號、問題、影響的框架、嚴重度

### 5. 提出建議

- 依影響程度排序，最多列出 5 項最重要的建議
- 每項建議包含：
  - 解決的問題：寫出第 4 步的問題編號（例如「問題 1、2」）
  - 具體做法（盡量用使用者現有的角色、道具、設定，不憑空發明新世界觀）
  - 預估開發成本：低、中、高
  - 預期改善哪些分數
- 同時指出「可以刪減」的部分，不只是加東西
- 若使用者有時程或範圍限制（例如六週 MVP），建議要符合限制

### 6. 遊測檢核清單

附上一份可在實際遊測時觀察與記錄的指標，例如：
- 規則解釋時間
- 第一局玩家的提問數量與內容
- 語音頻道的安靜時段
- 玩完主動想再玩一局的比例
- 必勝法在第幾局出現
- 玩家最常提起或大笑的時刻

## 輸出格式

使用使用者的語言撰寫。依序包含：

1. **一句話結論**：整體趣味性與複雜度判斷
2. **評分總表**：六個框架各自的分數與一句話理由（行動裝置上避免寬表格時，改用條列）
3. **各框架詳細檢核**：依據、證據、問題點
4. **問題點**：編號的問題總表，含影響的框架與嚴重度
5. **優先建議**：最多 5 項，每項標出解決的問題編號，含成本與預期影響
6. **可刪減項目**
7. **遊測檢核清單**
8. **資訊不足與假設**：列出評分時缺少的資訊與所做的假設

若內容很長或使用者需要保存、與團隊分享，產出為文件；簡短檢核則直接在回覆中呈現。

## 注意事項

- 評分要有證據，引用使用者的具體規則或內容，避免空泛評論
- 不要因為使用者投入很多心力就給高分；分數要誠實
- 尊重使用者已拍板的決定，建議以「在此前提下」提出；若某個決定是主要問題來源，可以指出並說明理由，但由使用者決定
- 喜劇或敘事類內容（台詞、反應）也要檢核：是否支撐目標美學、是否能在不知背景的情況下被理解
